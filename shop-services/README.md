# Сервисы shop — лабораторная 3, часть 0

Это отдельный Go-модуль на основе API из `tim44ik/itmo-container-labs`.
Исходный коммит: `138d7525c17bd6ce037b180a08187429961b9dd7`.
Существующая папка `api/` в корне вашего репозитория не изменяется.
Папки `shop-services/api/` и `shop-services/worker/` содержат две программы.
Общие пакеты находятся в `handlers/`, `telemetry/`, `internal/`.

## Что реализовано

API (порт 8080):

- `GET /health` — `ok`; при `HEALTH_FAIL=true` отвечает 503. Проверяет жизнь процесса, не зависит от БД.
- `GET /ready` — проверяет соединение с БД; дополнительная диагностическая ручка. Не проверяет наличие таблицы.
- `POST /order` — принимает `{"item":"book","quantity":2}`, сохраняет заказ, возвращает HTTP 201 и JSON.
- `GET /orders` — последние 100 заказов, новые первыми; `?limit=1..1000` меняет ограничение.
- `GET /metrics` — метрики Prometheus.
- Сохранены вспомогательные ручки `/slow`, `/fail`, `/load`, `/eat`, `/burn`.
- На `/order` и `/orders`: счётчики запросов/ошибок, гистограмма задержек, JSON-логи, серверные и вложенные DB-спаны.
- Заголовок ответа `X-Trace-ID` связывает запрос с логом и трейсом.

Worker (отдельный контейнер, порт 8080):

- Раз в секунду получает один pending-заказ и атомарно переводит его в processed.
- `FOR UPDATE SKIP LOCKED` в транзакции позволяет запускать несколько worker без повторной обработки одного заказа.
- При сбое до commit транзакция откатывается, заказ остаётся pending.
- Это демонстрация изменения статуса в одной БД, не гарантия exactly-once для внешних платежей/доставок.
- `/health` поддерживает HEALTH_FAIL и обнаруживает остановку рабочего цикла; недоступность БД логируется и повторяется без немедленного падения процесса.
- `/ready` проверяет соединение с БД.
- `/metrics`: `worker_orders_processed_total`, `worker_errors_total`, стандартные Go/process-метрики.
- `process-order` продолжает trace context заказа, записанного API в БД.

## Переменные окружения

| Переменная | API | Worker |
|---|---|---|
| DATABASE_URL | Обязательна | Обязательна |
| OTEL_EXPORTER_OTLP_ENDPOINT | `http://jaeger.monitoring.svc.cluster.local:4318` | То же |
| OTEL_SERVICE_NAME | Рекомендуется `shop-api` | Рекомендуется `shop-worker` |
| HEALTH_FAIL | `false` обычно; `true` для эксперимента | Аналогично |
| LISTEN_ADDR | По умолчанию `:8080` | По умолчанию `:8080` |

DATABASE_URL передаётся через Kubernetes Secret, не коммитится. Формат:
`postgres://USER:PASSWORD@DB_SERVICE:5432/shop?sslmode=require&connect_timeout=3`.
Спецсимволы в URL кодируются. Для локального PostgreSQL без TLS можно явно выбрать `sslmode=disable`;
для оператора БД режим согласуется с его настройками. `require` шифрует трафик, но не заменяет verify-full с CA.
Каждая реплика использует максимум 5 подключений к БД. Учитывайте суммарный пул при масштабировании.

## Сборка (в Ubuntu, из корня вашего репозитория)

```bash
docker build -t shop-api:v1 -f shop-services/api/Dockerfile ./shop-services
docker build -t shop-worker:v1 -f shop-services/worker/Dockerfile ./shop-services
```

Контекст обеих сборок — `shop-services`, а не вложенная папка api/worker.
Образы используют multi-stage, scratch и UID/GID 65532. Go на хосте не требуется.
Имена образов перед установкой политик согласуем с разрешённым реестром.

## База и миграция — обязательно перед запуском магазина

PostgreSQL устанавливается позже через CloudNativePG; в этом архиве нет Helm-чарта и оператора.
Создание базы/пользователя выполняет оператор. После этого тот же образ API запускается один раз
с аргументом `migrate` и переменной DATABASE_URL. В будущем чарте это отдельный Job.
Команда `/api migrate` создаёт таблицу и индекс; повторный запуск допустим.
Схема защищена транзакционной advisory-блокировкой от одновременной миграции нескольких процессов.
Обычный старт `/api` сам таблицу не создаёт. До миграции запросы заказов будут возвращать 503.

После установки сервисов и проброса API на локальный порт 18080:

```bash
curl -i http://localhost:18080/health
curl -i -X POST http://localhost:18080/order -H 'Content-Type: application/json' -d '{"item":"book","quantity":2}'
curl -s http://localhost:18080/orders
```

Worker может обработать заказ сразу: ответ POST показывает pending на момент вставки,
а ближайший GET уже может показать processed. `processed_at` подтверждает обработку.
Некорректный JSON, пустой item, quantity вне 1..1000 дают 400; неподходящий HTTP-метод — 405.
При недоступности БД операции имеют тайм-аут и возвращают 503, а не бесконечно зависают.

## Мониторинг и лабораторная 4

Для заказов фильтруйте метрики по `path="/order"` и job магазина; старый job/дашборд автоматически
новый чарт не подключит. ServiceMonitor и алерты будут добавлены в shop-чарт позже.
Унаследованный `/load` увеличивает демонстрационный счётчик; он не создаёт заказы.
Для лабораторной 4 используйте реальные POST-запросы к `/order` из k6/hey.
Гистограмма включает границу 0.3 секунды для SLA «95% быстрее 300 мс».
Удобно проверять долю bucket{le="0.3"}/count, не только интерполированный p95.
Повторная доставка POST без idempotency key создаёт отдельный заказ — учитывайте это в нагрузочном тесте.
Листинг ограничен, обработка заказов имитируется изменением статуса, без внешних побочных эффектов.

## Проверки

`go test ./...` проверяет HEALTH_FAIL, методы и валидацию запросов.
Полный запуск с PostgreSQL и двумя worker необходимо проверить в кластере после установки БД.
Результаты локальной проверки сборки находятся в VERIFICATION.txt.
